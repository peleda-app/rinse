# Decisions

rinse was formed on 2026-11-25 by merging two repositories that had no commits: `washer` (the generic sandbox, walls 1 and 2) and `peleda-content` (untrusted mail bytes to the safe document model, wall 3). Both decision histories are kept below under their original numbers and with the names of their time; a reference such as "From washer, 13" points into them. Name map: `washer-<x>` became `rinse-<x>`, `peleda-content` became `rinse-mail`, `peleda-content-<x>` became `rinse-mail-<x>`, `peleda-doc-model` and `peleda-text` became `rinse-doc-model` and `rinse-text`, `apps/content-worker-host` became `apps/rinse-worker`, and the app's sidecar `peleda-content-sidecar` became `rinse-worker`. Decisions taken since the merge follow at the end.

## From washer

Taken while extracting this repository from `../app` on 2026-11-25 (autonomous run; the maintainer agreed the repository map in `../baton/docs/PLAN.md`, "Repositories around Baton").

1. **Plain move, no history.** `app` had no commits; the code was moved, package names changed from `peleda-sandbox*` to `washer-sandbox*`, and `app` keeps no copy. The worker command-line arguments changed accordingly: `--washer-sandbox-policy=` and `--washer-sandbox-probe` (a worker and its parent always come from the same build, so no compatibility shim).
2. **One contract, three libraries.** `washer-sandbox` stays the only contract crate (with swappable `-linux`, `-macos`, `-none` implementations and the conformance suite). `washer-wasm`, `washer-process` and `washer-host` are libraries: each has exactly one implementation and their callers (`peleda-content-wasm`, `peleda-content-process`) wrap them behind their own contract. A generic "runner" trait was left out until a second implementation exists.
3. **The component stays a `wasi:cli/command`.** The bytes-in/bytes-out function is stdin to stdout with exit status 0. A custom WIT world exporting `run(list<u8>) -> list<u8>` would remove the WASI imports entirely, but exporting functions from a Rust component needs `#[unsafe(export_name)]` and generated unsafe glue, which the unsafe policy forbids outside OS FFI. Revisit when `wit-bindgen` can generate exports without unsafe in the guest, or when the policy allows generated code.
4. **Epochs, not fuel.** Time is bounded by epoch interruption (a 5 ms ticker per compiled component): no per-instruction cost and a wall-clock budget, which is what callers state. Fuel would make budgets deterministic across machines; not needed yet.
5. **Generic errors.** `WasmError` and `ProcessError` are small closed enums with no data from the worker; callers map them to their own errors (`peleda-content` maps them one to one onto `ContentError`).
6. **Output limit includes everything the component writes.** `washer-wasm` knows no status byte; a caller that frames its output adds its framing to the limit (`peleda-content-wasm` passes `max_output_bytes + 1`).
7. **`washer-process` checks the request size** (`RequestTooLarge` above the 512 MiB a worker reads) before starting anything, so an oversized request never costs a process.
8. **The serve loop lives in `washer-process::worker`, the platform pick in `washer-host`.** `worker_main` stays usable with any `Lockdown` (tests use it with fault workers), while `washer_host::run` is the one-call child side for WebAssembly workers. `Serve::warm_up` replaced the content-specific built-in render; each handler warms itself up with trusted input.
9. **`washer-build` is shared.** The nested `cargo build --target wasm32-wasip2` logic (toolchain fallback through rustup, cleared wrapper variables, separate target directory) moved out of `content-wasm`'s build script into a build-dependency crate, used by `washer-wasm-fixtures` here and `peleda-content-wasm` downstream. Nested target directories end in `-component` so they never collide with a binary of the same name in a shared target directory (this machine sets a global `CARGO_TARGET_DIR`).
10. **A test component of our own.** `washer-wasm-test-worker` (built by `washer-wasm-fixtures`, dev-dependency only) gives washer tests a misbehaving component without depending on any user of washer.
11. **The Linux image is slimmer.** `tests/linux/Dockerfile` drops the WebKit and GTK packages `app` needs for Tauri; it keeps the toolchain, clippy, rustfmt and `wasm32-wasip2`. The target directory inside the container is pinned to a Docker volume (`CARGO_TARGET_DIR=/work/washer/target`) so a host-wide `CARGO_TARGET_DIR` cannot leak in.
12. **Fuzz targets outside the workspace.** `fuzz/` (its own `[workspace]` and lock file) holds libFuzzer targets for `read_frame` plus `decode_announcement`, `decode_announcement` alone and `Policy::from_args`, each a one-line call into `washer_sandbox::fuzz` (hidden public module). `cargo fuzz` needs nightly, which is not set up here, so they have not been fuzzed yet; `mise run check` compiles and formats them on stable, and `washer-sandbox`'s unit tests feed the same entry points truncated, bit-flipped and length-lying variants on every `cargo test`. `read_frame` now grows its buffer with the bytes that actually arrive instead of allocating the announced length up front.
13. **Departure from the agreed repository map.** `../baton/docs/PLAN.md` ("Repositories around Baton") puts `content-wasm`, `content-process` and the worker host binary in washer. They went to `../peleda-content` instead (`peleda-content-wasm`, `peleda-content-process`, `apps/content-worker-host`), and washer got the generic libraries they now wrap (`washer-wasm`, `washer-process`, `washer-host`). Reason: all three speak the content protocol (`RenderRequest`, `Rendered`, `ContentError`, the hostile corpus, the content worker component), and washer must stay free of anything mail-specific so other untrusted parsers can use it. The PLAN.md table in `../baton` (not editable from this run) should be updated to match by the next Baton session.
14. **Nested target directory per feature set.** A build script that builds the same binary with different features gives each feature set its own `nested_target_dir` (as `peleda-content-wasm` now does for its shipped and test-hooks workers): cargo only locks per profile, so two outer builds in a shared target directory could otherwise copy each other's file.
15. **`probe` cannot reach a release build.** `washer-host` fails to compile with the `probe` feature unless `debug_assertions` are on; the probe tests run in debug in `mise run check`.
16. **macOS `SIGIO` exception is documented and asserted.** Seatbelt does not deny `fcntl(F_SETOWN, <other pid>)` with `O_ASYNC`, so a locked-down worker can have `SIGIO` sent to a process it may signal. The threat-model docs (WALLS.md, `../app/docs/ISOLATION.md`) say so, and the conformance suite asserts `Allowed` on macOS so a change either way is noticed.
17. **Stricter unsafe gate.** `scripts/check-unsafe.sh` (same script in `../peleda-content` and `../app`) catches `allow`, `expect` and `warn` of `unsafe_code` or `clippy::undocumented_unsafe_blocks` anywhere in an attribute list, and fails for any crate manifest under `crates/` or `apps/` without `[lints] workspace = true`.

### Fuzzing and CI (2026-11-25, autonomous run)

18. **Fuzzing is run, not only compiled.** `fuzz/rust-toolchain.toml` pins `nightly-2026-10-01` (the nightly `../baton` and `../skein` pin, already installed here); `fuzz/run.sh` and `mise run fuzz` build and run every target for N seconds (same script as Baton's, plus read-only seed directories from `fuzz/seeds` and a private `fuzz/target`: this machine shares one global `CARGO_TARGET_DIR`, and Baton has a target called `frame` too). Sanitizers stay off (`-s none`): the code is safe Rust, so panics and failed assertions are the signal, and executions are several times faster. This supersedes the "not fuzzed yet" part of the earlier fuzz decision.
19. **CI in `.github/workflows/ci.yml`** (see [CI.md](CI.md)): macOS aarch64 runs `mise run check`; Linux runs `scripts/check-linux.sh` in the repository's own check image on `ubuntu-24.04-arm` (arm, like the machines it was verified on); the Windows job cross-checks from macOS with `mise run check-windows` instead of using a Windows runner, because that is exactly what is verified locally and a native runner adds only the Wasmtime crates (which need the Windows SDK); fuzzing runs nightly and on demand, not on pull requests, to keep pull requests fast. Actions are pinned by commit SHA (tags resolved 2026-11-25), permissions are `contents: read` per job and nothing at the top.
20. **`frames` target.** Beyond the three one-call targets, `frames` reads a stream of frames under a cap from the first byte and checks the round trips of `write_frame`/`read_frame` and `announce`/`decode_announcement` (the report). The async frame readers of the launchers are not fuzzed directly (they need a child process); they share `frame_len` and the cap check with `read_frame`, and allocate at most the caller's cap.
21. **Linux CI cache.** `tests/linux/run.sh` takes `LINUX_CACHE_DIR` to put the registry and target directory in host directories (cached by `actions/cache`) instead of named volumes. The Linux job uses Docker's default seccomp profile, the configuration the conformance suite is documented to pass with namespaces reported missing.
22. **Result of the first run** (60 s per target, macOS aarch64): `announcement` 54 million executions, `frame` 53 million, `frames` 4.4 million, `policy` 30 million; no failure.
23. **CI review.** Cancel-in-progress only on pull requests, so every push to `main` gets a complete run. The Linux job restores its cache always and saves it only on pushes to `main` when the key (no commit SHA) missed, after dropping `incremental/`. The fuzz job stays on `ubuntu-24.04-arm` and builds `cargo-fuzz` 0.13.2 from source with `--locked` on the pinned nightly, kept in `~/.cargo/bin` by rust-cache (`taiki-e/install-action` has no manifest for it and there is no prebuilt aarch64 Linux binary). `washer-sandbox::fuzz` stays unconditional for now (it only calls the crate's own validators); `../app` gated its fuzz modules behind a `fuzz` feature.

## From peleda-content

Taken while extracting this repository from `../app` on 2026-11-25 (autonomous run; repository map agreed in `../baton/docs/PLAN.md`, "Repositories around Baton").

1. **Plain move, package names kept.** `peleda-content`, `-engine`, `-worker`, `-direct`, `-wasm`, `-process`, `peleda-doc-model`, `peleda-text` and `apps/content-worker-host` (`peleda-content-worker-host`) moved with their directories; `app` keeps no copies and depends on them by path.
2. **Thin adapters over washer.** `peleda-content-wasm` keeps only the worker protocol, limit and error mapping and validation over `washer-wasm`; `peleda-content-process` keeps the request frame, response cap, error mapping, validation and the worker-side `ContentHandler` over `washer-process`. Public APIs stayed source-compatible for `app` (`WasmContent::{embedded, from_component, render_blocking, decode_part_blocking}`, `ProcessContent`, `ProcessConfig`), with `WasmContent::from_runner` added.
3. **`worker::Serve` became `worker::BlockingContent`** in `peleda-content-process`, because `washer_process::worker::Serve` is now the generic byte-level trait; `ContentHandler<C: BlockingContent>` adapts one to the other. The built-in warm-up message moved into `ContentHandler::warm_up`.
4. **The content-process conformance test uses `washer_host::run`** for its real worker, so it exercises the same stack as the shipped executable.
5. **Fixtures by API, not path.** `app`'s core tests read the corpus through `peleda_content::testing::fixture` instead of `include_bytes!("../../content/fixtures/...")`.
6. **No unsafe code here.** `unsafe-allowlist.txt` is empty; the OS sandbox FFI is in `../washer`.
7. **Linux image.** `tests/linux/run.sh` mounts this repository read-write and `../washer` read-only at the same relative place, with the target directory pinned to a Docker volume. `PELEDA_DOCKER_FLAGS` passes extra flags.
8. **Fuzz targets outside the workspace.** `fuzz/` (its own `[workspace]` and lock file) holds libFuzzer targets for the worker request decoder (`worker_request`), the MIME, HTML and image pipeline (`render_raw`), the host's decoding and verification of a worker's answer (`host_response`) and `peleda_doc_model::decode` (`doc_model`). `cargo fuzz` needs nightly, which is not set up here, so they have not been fuzzed yet; `mise run check` compiles and formats them on stable, and `crates/content-worker/tests/untrusted_inputs.rs` feeds the same entry points the hostile corpus plus truncated, bit-flipped and length-lying variants on every `cargo test`.
9. **Departure from the agreed repository map.** `../baton/docs/PLAN.md` puts `content-wasm`, `content-process` and the worker host binary in `../washer`; they are here instead, because they speak the content protocol and washer stays generic ("From washer", 13). The table in `../baton` still shows the old split.
10. **One nested target directory per worker feature set.** `peleda-content-wasm`'s build script builds the shipped worker in `<target>/peleda-content-worker-component` and the test-hooks worker in `<target>/peleda-content-worker-test-component`. Sharing one directory let a concurrent debug build (cargo locks only per profile, and this machine shares one global target directory between `app` and this workspace) hand the test-hooks component to the release build as `EMBEDDED_WORKER`. The test `shipped_worker_has_no_test_hooks` checks that the embedded worker differs from the test one and does not answer the `PELEDA-TEST-*` inputs.
11. **blake3 is `pure` on Windows.** `peleda-content` and `peleda-content-engine` turn on blake3's `pure` feature for `cfg(windows)` only, so the crates that do not use Wasmtime compile for `aarch64-pc-windows-msvc` without a Windows C toolchain (blake3's NEON C file needs one). Other targets keep the C/assembly implementations.

### MessageFacts (2026-11-25, autonomous run)

Implemented from `../peleda-insight/docs/ARCHITECTURE.md` ("What peleda-content provides") and its QUESTIONS 1. Open details decided here:

12. **Facts travel in `Rendered`.** `Rendered::facts: MessageFacts` (last field, so the postcard layout of older fields is unchanged), extracted by the engine inside the worker and checked by `verify_facts`, which `verify_rendered` calls; no separate request or call.
13. **Signals as a typed bit set.** `HeaderSignals(u32)` with `HeaderSignal` positions 0 to 10 in Holtmail's order (`list_id` … `noreply`); Holtmail's bits 11 (`forward_marker`) and 12 (`structured`) are not header signals and are derived from `layout.forward_at` and `structured` instead. The receiver rejects unknown bits: worker and host ship together.
14. **Authentication facts keep every method, typed.** Each result is `{ method: AuthMethod, result: AuthOutcome, domain, identity }` with closed enums instead of strings; `domain` only for DKIM (`header.d`, else the domain of `header.i`), SPF (domain of `smtp.mailfrom`) and DMARC (`header.from`); `identity` only for DKIM. `position` counts every field from the top, including unreadable ones, so consumers can trust only the position their own server writes. The grammar is a port of Holtmail's `auth-results` (same author, MIT/Apache-2.0).
15. **Unsubscribe targets are strict.** Only the first `List-Unsubscribe` field; only `https` (not `http`, because RFC 8058 one-click requires https and a POST is a request the node makes) with a public host per `remote_image_url_ok`; `mailto` only with one address and no header field but `subject` and `body` (any other field, `bcc` included, drops the target rather than being stripped, since an automated unsubscribe mail must not go anywhere else). Items with control characters are dropped. The percent-decoded address may not contain `?&=%#/` (nor address separators), even though RFC 5322 allows some of them in a local part: an address like `x?bcc=...@example.com` would turn into a header field when a consumer rebuilds the URL, and real unsubscribe addresses do not use them; the worker drops such targets and `verify_facts` rejects them. `one_click` needs exactly one `List-Unsubscribe-Post` field equal to `List-Unsubscribe=One-Click` and an https target.
16. **References keep the first and the last 31 ids**, read in constant memory, with `references_cut`.
17. **Times and money without floats or zones.** `When::{Instant, Local, Date}` within 1970 to 2200 (no time zone database in the worker; a calendar `TZID` is passed through as `time_zone`), `Price { amount: decimal string, currency }`.
18. **Structured data: JSON-LD only, plus Wallet passes.** Microdata is not read (Holtmail read it; it can follow). URLs in items must pass `remote_image_url_ok` (public `http(s)` host, no userinfo). Passes come from `.pkpass` attachments through a small zip reader (`miniz_oxide`, already in the tree through `png`) instead of the `zip` crate; the signature is not checked.
19. **Layout facts are computed on the finished body**, with block indices in depth-first pre-order of `Rendered::body`, so the receiver can check them; button hints and `aria-label`s come from the HTML walk. Placement is that of a link's first occurrence (links are merged per destination). The footer rule follows Holtmail: first unsubscribe link or `©`.
20. **Fact strings do not count in `Findings`**: cleaning them uses a scratch counter, so `header_text` keeps meaning header fields and file names.
21. **Layout and size.** Facts are not dropped to fit `max_output_bytes`; they are small by construction (caps above), and a response that does not fit fails as before.

(a) A zero-width joiner between an emoji and collapsed whitespace (`❍ ‍❍`) was kept on the first pass, because the emoji before the space still counted as the previous character, and dropped on the second; the joiner is now kept only when no whitespace is pending (`joiner_after_collapsed_whitespace_is_dropped_so_output_is_stable`). (b) A cut could end in `❍‍…` (a joiner that `unicode-segmentation` keeps in the emoji's grapheme when what follows is not `Extended_Pictographic`, though `is_emoji_part` accepted it), and the second pass dropped the joiner before the `…`; trailing joiners are now removed before the `…` (`cut_never_ends_in_a_joiner_so_output_is_stable`).

Its corpus starts with the inputs of 26 above and both whole `../app` snapshot inputs that found them. First run: 1.3 million executions in 40 s, no failure.
29. **Worker answers are compared, not only survived.** `decode_part` and `render_raw` decode the worker's response frame and assert it equals the engine's direct result, value or error kind, since the host's walls assume both paths are equivalent. 40 s each after the change: 226 thousand and 5.8 thousand executions, no failure.

### Seams review (2026-11-25, autonomous run)

31. **`verify_facts` checks what the payload can confirm about `one_click` and `time_zone`.** `one_click` now also needs `field_counts.list_unsubscribe_post == 1` and the `UnsubscribePost` signal, and `time_zone` needs a `When::Local` start, as documented; before, a receiver got `one_click` without the one-field half of its meaning (`../peleda-insight` re-checked the counts itself). Cases in `rejects_each_broken_guarantee` (the first new one failed on the old code) and `time_zone_with_a_local_start_is_accepted`.
32. **A prebuilt worker cannot be the test-hooks worker.** `content-wasm/build.rs` builds the test artifact first and fails when `PELEDA_CONTENT_WORKER_WASM` has the same bytes (probed: the build fails with the test worker as the prebuilt). `../app/scripts/build-worker-host.sh` passes the variable on only with a matching `PELEDA_CONTENT_WORKER_WASM_SHA256`.
33. **Downstream signal bits map by name.** `HeaderSignal` positions stay append-only; `../peleda-insight` maps them to its own persisted `Signal` positions through an exhaustive match, so a new signal here breaks its build instead of landing on its bit 11 (`forward_marker`).

### Trust review (2026-11-25, autonomous run)

34. **Link hosts and warnings are derived, not reported.** `verify_rendered` let a compromised worker set `display_host` to any display string and clear any destination warning, and the app showed both next to the link (`attack_lying_worker_link_host_and_warnings_are_rejected`). `link_destination` and `text_names_other_host` now live in the contract; the engine builds `LinkInfo` with them (the display host is no longer passed through `text::display`, it is the IDNA Unicode form, or the ASCII host when that form is not a display string) and `verify_rendered` requires equality for `display_host`, `punycode`, `mixed_script`, `ip_host`, `userinfo` and `text_href_mismatch`. Equality rather than "at least": every flag is a pure function of `href` and `text`, and merged occurrences of one destination keep the text that names another host, so honest output always matches.
35. **Decoding a render response is bounded by the limits, not by the response size.** A 1-byte `Block::Divider` became about 120 bytes of heap (wire node plus block) before `verify_rendered` could refuse it: 48 MiB of output meant about 6 GB. Every `Vec` of `Rendered` (byte buffers excepted) and the document's wire nodes now read through `peleda_doc_model::bounded_vec` under `with_decode_budget`; `decode_render_response` sets `render_decode_budget(limits)` and is used by the process and WASM adapters; `peleda_doc_model::decode` sets `max_blocks + max_inlines`. Measured in a scratch probe with a counting allocator: the 4,000,000-divider response now fails at its declared length with no allocation (was 492 MB, ratio 123); the worst accepted body (120,000 nodes) peaks at about 43 MB. Strings and byte buffers still cost their encoded size, so peak memory is at most about that plus `max_output_bytes`. Tests: `attack_lying_worker_divider_flood_is_refused_while_decoding`, `attack_lying_worker_empty_link_flood_is_refused_while_decoding`, `attack_node_flood_stops_while_decoding`. The repository forbids `unsafe`, so the tests assert where decoding fails, not the allocator peak. `max_output_bytes` stays 48 MiB because images are carried in it.

## Merge into rinse (2026-11-25, autonomous run)

Stage 3 of the workspace reorganisation (`../reorg-plan.md`). `../washer` and `../peleda-content` had no commits; they were copied, not moved, and stay on disk untouched as retired sources.

1. **One workspace, one lock file.** Members are `crates/*` and `apps/rinse-worker`. `Cargo.lock` started from `peleda-content`'s (a superset of `washer`'s apart from washer's two test crates) with the package names rewritten, then cargo resolved offline and only added `rinse-wasm-fixtures` and `rinse-wasm-test-worker`: postcard 1.1.3, serde 1.0.229 and wasmtime 51.0.0 are unchanged, and so is every other version.
2. **Names.** Package prefix `rinse-`, directories without it. `washer-<x>` became `rinse-<x>` in `crates/<x>`; `peleda-content` became `rinse-mail` in `crates/mail`, `peleda-content-<x>` became `rinse-mail-<x>` in `crates/mail-<x>`, `peleda-doc-model` and `peleda-text` became `rinse-doc-model` and `rinse-text`. Rust paths, features (`rinse-host/probe`, `rinse-wasm/pulley`, `rinse-sandbox/testing`), nested component directories (`<target>/rinse-mail-worker-component`, `-test-component`, `rinse-wasm-test-worker-component`), embedded artifact names and the test-hook markers (`RINSE-TEST-*`) follow.
3. **The worker executable is package `rinse-worker` with binary `rinse-worker-host`.** The app copies it to `binaries/rinse-worker-<triple>` and Tauri copies that next to the shell as `rinse-worker`; with this machine's shared `CARGO_TARGET_DIR`, a cargo binary named `rinse-worker` would share `<target>/debug/rinse-worker` with Tauri's copy, and a debug build with the `probe` feature could end up next to a development shell. This keeps the reason the old names differed (`peleda-content-worker-host` and `peleda-content-sidecar`) and still gives the package and the sidecar the agreed name.
4. **Worker interface names.** `--rinse-sandbox-policy=`, `--rinse-sandbox-probe` (and its `-exit-early` and `-bad-announcement` variants) replace the `--washer-sandbox-*` arguments with no shim, as before ("From washer", 1): worker and parent come from the same build. `policy_arguments_of_older_names_are_not_understood` keeps the old `--washer-sandbox-policy=` and `--peleda-sandbox-policy=` refused. `RINSE_MAIL_WORKER_WASM` and `RINSE_MAIL_WORKER_WASM_SHA256` replace `PELEDA_CONTENT_WORKER_WASM*` (named after the mail worker, so a later files worker gets its own variable); `RINSE_DOCKER_FLAGS` replaces `WASHER_DOCKER_FLAGS` and `PELEDA_DOCKER_FLAGS`.
5. **The `peleda-image:`, `peleda-remote:` and `peleda-link:` schemes stay.** They are a wire contract with the app's webview and CSP, not a crate name; renaming them is a cross-repository change left to the maintainer (QUESTIONS 1).
